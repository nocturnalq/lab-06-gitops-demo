# Лабораторная работа 6. GitOps

Задание по доставке в Kubernetes по модели GitOps: кластер сам приводит себя к состоянию, описанному в ветке `master` вашего репозитория на GitHub.
Сервис `notes` из лабораторных 3-5 переезжает из Gitea на GitHub, его CI - на GitHub Actions, а деплой из конвейера заменяет Flux, установленный через Flux Operator в локальный кластер [kind](https://kind.sigs.k8s.io/).

## Пререквизиты

- Лабораторные работы 3, 4 и 5 выполнены: код `notes` лежит в Gitea, манифесты `notes` и `gateway` из лабораторной 4 и values стека мониторинга из лабораторной 5 у вас есть.
- Контейнер `lab-01-pipeline-task-1` из лабораторной 3 запущен (порт 3000 опубликован на `127.0.0.1`), а его тома не удалены.
- Аккаунт на GitHub.
- Docker (Docker Desktop, OrbStack или Docker Engine) и не меньше 8 ГБ свободной памяти для кластера из трех узлов со стеком мониторинга.
- [kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation), [kubectl](https://kubernetes.io/docs/tasks/tools/), [helm](https://helm.sh/docs/intro/install/) и git актуальных версий, по желанию CLI [flux](https://fluxcd.io/flux/installation/#install-the-flux-cli) 2.10.
- Свободные порты `8080` и `12000`-`17000` на `127.0.0.1`: на них проброшены шлюз `notes` и интерфейсы мониторинга.
- Доступ в интернет для скачивания образов и helm-чартов.

## Темы

- GitOps: декларативность, версионирование, pull-модель, непрерывная сверка;
- Flux и Flux Operator: `FluxInstance`, `GitRepository`, `Kustomization`, `HelmRelease`;
- GitHub Actions, `GITHUB_TOKEN`, GitHub Container Registry, образы для нескольких архитектур;
- автоматическое обновление образов: `ImageRepository`, `ImagePolicy`, `ImageUpdateAutomation`;
- откат и секреты в GitOps.

## Как сдать отчет

1. Сделайте форк этого репозитория.
2. В своем форке создайте ветку, например `ivan_petrov-lab-06-task-1`.
3. Скопируйте [REPORT_TEMPLATE.md](REPORT_TEMPLATE.md) в `reports/<ник_тг>/<ID задания>/REPORT.md` и заполните его.
   Скриншоты положите в ту же папку и вставьте в отчет относительными ссылками, например `![flux](01-flux.png)`.
   Манифесты, workflow и `FluxInstance` копировать не нужно: преподаватель смотрит их в вашем репозитории `notes`.
4. Откройте Pull Request в этот репозиторий с названием `<ник_тг>-<ID задания>`, например `ivan_petrov-lab-06-task-1`.
   Одно задание - один PR.

`<ник_тг>` - ваш ник в Telegram без `@`: латинские буквы, цифры и `_`, от 5 до 32 символов.
`<ник_k8s>` - тот же ник в нижнем регистре, в котором `_` заменен на `-` (например, `ivan-petrov` для `Ivan_Petrov`): так называются кластер kind и пространство имен сервиса, потому что их имена допускают только строчные буквы, цифры и `-`.
`<github_user>` - ваш логин на GitHub.

PR не нужно вливать: преподаватель проверит отчет и оставит комментарии в PR.

## Автоматическая проверка PR

При открытии и обновлении PR запускается проверка `check-report`.
Она не оценивает решение, а только проверяет оформление:

- название PR имеет вид `<ник_тг>-<ID задания>`, и такое задание существует;
- PR меняет только файлы в `reports/<ник_тг>/<ID задания>/`;
- в этой папке есть `REPORT.md`;
- в отчете встречается контекст `kind-<ник_k8s>`, то есть кластер назван вашим ником;
- в отчете есть ссылка на репозиторий `https://github.com/<github_user>/notes`;
- в файлах отчета нет токенов (включая токены GitHub) и закрытых ключей.

Если проверка не прошла, исправьте PR: она запустится снова при каждом новом коммите или изменении названия.

## Безопасность отчетов

Все PR в этом репозитории видны всем участникам курса.
Никогда не публикуйте в отчете пароли (включая пароль от Grafana), токены GitHub (`ghp_...`, `github_pat_...`), ключи и kubeconfig целиком: заменяйте их на `<пароль>`, `<токен>`, `<ключ>`.
Токены и пароли не должны попадать и в ваш репозиторий `notes`: Secret-ы в кластере создаются руками.
Если секрет все-таки попал в PR или в репозиторий, удалить коммит недостаточно: отзовите токен на GitHub и смените пароль.

## Уникальность отчетов

Каждый отчет должен быть вашим собственным:

- кластер kind и пространство имен сервиса называются `<ник_k8s>`, поэтому на всех скриншотах и в выводах команд видны имена узлов `<ник_k8s>-control-plane`, `<ник_k8s>-worker` и пространство имен `<ник_k8s>`;
- история коммитов, запуски workflow и коммиты автоматизации Flux видны в вашем репозитории `notes`;
- в конце отчета приведен вывод проверочной команды из критериев приемки задания;
- объяснения написаны своими словами.

Отчеты, совпадающие по содержанию с чужими, не засчитываются.
